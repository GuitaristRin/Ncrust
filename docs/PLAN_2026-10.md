## 1. Android 更新检测与拉取

目标：有新版本时让用户**知道且能一键获取**，但**绝不打断**正在听歌的用户。Windows 已有同类实现（f5f9f9d），沿用它的规则：发布走滚动班次（tag `CrateStack-YYYYMMDD<序号>`，见 `docs/RELEASES.md`），按资产名 `ncrust-android-universal-<版本>.apk` 跨班次找严格更高的版本，不依赖 Latest 徽章。

设计要点：

- **何时检查**：冷启动后延迟到首页渲染完成再查；24 小时最多一次；用户在「关于」页可手动检查。只请求一次 `api.github.com/repos/GuitaristRin/Ncrust/releases`（未认证限额 60 次 / 小时 / IP，足够），忽略草稿与预发布。
- **怎么提示**（不弹窗）：底部导航「用户」图标上一个小圆点 + 用户页顶部一行「发现新版本 1.4.0 · 查看」。不弹 Dialog、不发通知、不在播放时打扰。用户点「稍后」后该版本不再提示，直到下一个版本。
- **更新页**：Kanesumi 风格的独立页，显示版本号、发布日期、大小与 release 正文（复用现有 `MarkdownText`），一个「下载并安装」按钮。
- **下载与安装**：应用内下载到 `cacheDir`，进度条在更新页内（不发通知栏进度，避免和播放通知抢位）；完成后校验 APK 签名与当前应用一致、`versionCode` 更大，再交给系统安装器（`REQUEST_INSTALL_PACKAGES` + `FileProvider`）。签名不一致（如测试版用临时密钥）时如实提示「需卸载后安装」而不是失败。
- **国内网络**：GitHub 资产下载在国内可能很慢或中断——支持断点续传；失败时提供「在浏览器中打开下载页」的退路。是否加镜像源由负责人决定（涉及第三方信任）。
- **spec 先行**：版本比较、tag 解析、asset 选择规则进 `spec/fixtures/update/`，两端共用（Windows 已有实现，补夹具即可对齐）。

## 2. 性能第二轮

- **卡片展开 / 收起**：剩余成本在 RenderThread（每帧整屏合成大封面 + 多层全屏图层，8~11ms）。先查过度绘制与图层数，再看封面尺寸（满宽 1080px 必要，但收起态可用小图）。
- **方法级 baseline profile**（审计 S1）：现有 profile 是手写类级列表、含 5 条死条目，且从未自动生成。用 macrobenchmark 生成——它会卸载重装应用，需用 `benchmark/cookie.secret` 注入登录态。
- **媒体续播卡**：系统界面的「最近播放」续播连不上服务（实测起播时 3 次 `onConnectFailed`），实现 media3 `onPlaybackResumption`，应用被杀后锁屏 / 通知栏能一键恢复上次的歌。
- **Windows**：审计 W-01/W-02（窗口不可见时停掉计时器与动画）、W-05（首页虚拟化）——本机即可实测。
- 其余按两份审计报告的前 10 项依次推进，每项都要有前后对比数据。

## 3. 小屏按键机适配（荣悦 E5 一类）

设备事实（负责人提供的截图，`C:/Users/mc158/Desktop/rongyue-e5-preview`）：3.49 英寸 320×480、165 ppi（DevCheck 判 ldpi）、59 Hz；触屏 + 全键盘（方向键、确认键、通话 / 挂断键、0~9 数字键）。按 ldpi 约 427×640 dp 可用。

问题根因：全屏播放器的封面固定「满宽 + 1:1」，在矮屏上吃掉一半以上高度，加上控件区后歌词区被压到几乎为零。

方案（窗口尺寸驱动，而不是认某个机型）：

- **紧凑高度档**（`screenHeightDp` 低于阈值，候选 640dp）：全屏播放器默认进入「小封面 + 歌词」模式，封面缩成顶栏缩略图；控件区压成一行（上一首 / 播放 / 下一首 + 进度）；页头 34sp 降为更小字号；底部导航与迷你条高度收紧。
- **按键操作**：所有可点项可获得焦点且焦点态清晰可见（Kanesumi 直角焦点框）；方向键在列表 / 网格 / 底部导航间移动；确认键 = 点击；返回键 = 收起卡片 / 返回；数字键快捷：5 播放暂停、4/6 上下一首、2/8 音量，可在设置里关掉。
- **验证**：建 320×480 ldpi + D-pad 的模拟器配置做回归；如能联系到那位用户，发测试包请其回测（APK 体积与内存也要看：这类机器通常 1~2 GB 内存）。

## 4. 歌单工作链（参考 Apple Music）

先调研、出交互稿，经负责人确认再动手。调研范围：

- Apple Music 的歌单体验：从任意歌曲「添加到歌单」的统一入口、最近使用的歌单置顶、新建歌单后立即加入、编辑模式（拖拽排序 / 批量删除 / 改名 / 改封面与描述）、歌单底部的推荐曲目、马赛克封面、歌单文件夹、按添加时间 / 标题 / 歌手排序、搜索歌单内曲目。
- 映射到网易云接口：歌单增删改（create / delete / update name & desc）、曲目增删（`playlist/manipulate/tracks`）、曲目排序、收藏他人歌单（subscribe），并实测这些写接口是否存在与收藏相同的「事后回滚」风控（若有，同样迁到官方客户端同形通道）。
- 产出：`docs/playlists/research.md`（对照表与取舍）+ 交互稿，再拆分两端任务。

## 5. Walkman NW-F885 兼容版（可行性先行）

现状判断（未实测，需 spike 证实）：该机为 Android 4.1 世代（API 16），远低于当前 minSdk 24。Compose、media3、OkHttp 4 均要求 API 21+，现有代码无法直接降级。

可行路线只有「独立的精简客户端」：传统 View 界面 + 旧版播放器（MediaPlayer 或 ExoPlayer 2.x 的 API 16 兼容版本）+ OkHttp 3.12.x（API 9+）+ Conscrypt 提供 TLS 1.2（4.1 默认不启用 TLS 1.2，网易接口必须）。功能收缩到：登录（网页登录在 4.1 的 WebView 上很可能跑不动 → 改为导入 cookie / 扫码）、每日推荐、收藏、搜索、播放、歌词。

spike 只回答三个问题，然后再决定是否立项：

1. 在 4.1 上用 OkHttp 3.12 + Conscrypt 能否稳定访问 `music.163.com` / `interface*.music.163.com`（TLS / 证书链）。
2. 取链拿到的 mp3 / flac 能否用系统播放器正常播放（含无缝衔接的可能性）。
3. 负责人设备上的屏幕尺寸、内存与按键，以及能否安装第三方 APK。

### 5b. 若 4.1 撑不住直接运行：逆向立项（负责人 2026-10-15 提出）

方向：单独立项研究这台机器，以它为实验室——做基于 Linux 的自有 Rust 系统，或刷 LineageOS 一类系统——再把 F885 专属的部分移植过去。
等 spike 报告出来后再决定是否走这条路。2026-10-15 只读采集到的底层事实（adb，未写入设备）：

| 项 | 实测 |
|---|---|
| 内核 | Linux 3.0.31，2013-10 构建，GCC 4.4.3 |
| 引导链 | OMAP4 标准 `xloader`（mmcblk0p1）→ U-Boot 1.1.4（p2）；独立 boot（p7）/ recovery（p6）/ system（p14）/ userdata（p16）/ efs / nvp / configs 等分区 |
| 安全状态 | `ro.secure=1`、user 版、release-keys、无 su；**OMAP4 是 HS（只引导签名镜像）还是 GP 芯片未知**——这决定能否刷自有系统，是立项前第一个要查清的问题 |
| 音频 | Sony 自有 ALSA 声卡 `ICXAudioCard` + 私有 HAL `libmix.icx.so` / `libsrc.icx.so`（混音、采样率转换，疑似承载 DSEE / ClearAudio）——「F885 专属内容物」的核心，也是移植最难的部分 |
| 其它 | HDMI 声卡 `OMAP4HDMI`；`lights` / `sensors` / `power` / `nfc` 为 `icx1237` 专有 HAL；只有系统浏览器 |

立项前要先回答：Sony 是否公开了该机的 GPL 内核源码（含 ICX 音频驱动）；芯片 HS / GP；能否不破坏 efs / nvp（设备唯一数据）做完整备份；
有无可用的提权或官方 / 工厂刷机通道。逆向工作可以用 `reverse-engineer-anything` 技能对系统镜像与私有 HAL 做静态分析。

## 风险与未决

- 小屏方案与歌单方案都会改动大量界面，需在性能第二轮之后进行，避免互相掩盖性能回归。
- 更新检测涉及签名：测试机当前装的是临时密钥签名的包，正式更新流程只能在正式签名包上验证。
